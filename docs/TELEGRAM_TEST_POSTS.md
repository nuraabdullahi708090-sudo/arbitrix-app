# Controlled live tests (partner group + announcement channel)

Two single messages that prove delivery end to end without enabling publishing.
Both are sent by the **web service** through the existing admin route — the
marketing worker is not involved, no queue row is created, and `paused` /
`dry_run` are untouched.

Everything else is already deployed. This file is the final, owner-run step.

---

## 1. The two posts (exact copy, English)

Rendered by `renderTestMessage()` from `services/MarketingContent.js`, so the
text is generated by the deployed code, not typed by hand. It is short, states
that no action is needed, and makes no earnings or performance claim.

## 2. Preconditions (all verifiable with one command)

In the Render shell of the **web** service:

```bash
node scripts/check-marketing-readiness.js
```

It must report `READY` (or `READY_WITH_WARNINGS` whose only warning is the
missing worker). Specifically it tells you that:

* `TELEGRAM_MARKETING_CHAT_ID` and `TELEGRAM_ANNOUNCEMENT_CHAT_ID` are set,
  different from each other, reachable, and that the bot is an **administrator
  able to post** (and to pin, for the group);
* if the two ids are equal the channel is disabled by design and no channel
  test can be sent.

`TELEGRAM_MARKETING_ENABLED` does **not** have to be true for these two tests:
`POST /api/admin/marketing/test-send` is an explicit admin action, not the
worker.

## 3. Preview, then send

Both routes require an admin JWT (`Authorization: Bearer <jwt>`).

Preview (no message is sent, no row is written):

```bash
curl -sS "$BASE/api/admin/marketing/test-message?audience=group" \
  -H "Authorization: Bearer $JWT"
curl -sS "$BASE/api/admin/marketing/test-message?audience=channel" \
  -H "Authorization: Bearer $JWT"
```

The response carries `text`, `guard` (the safety verdict), `destinationConfigured`
and `destinationReason`.

Deliver the group message:

```bash
curl -sS -X POST "$BASE/api/admin/marketing/test-send" \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"audience":"group","confirm":"SEND TEST"}'
```

Deliver the channel message:

```bash
curl -sS -X POST "$BASE/api/admin/marketing/test-send" \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"audience":"channel","confirm":"SEND TEST"}'
```

`confirm` must be exactly `SEND TEST` (case-insensitive); without it the route
answers `400` and sends nothing.

---

## 4. What a success looks like

* HTTP `200` with `{"success":true,"audience":"...","messageId":<n>,"text":"..."}`
  and the note that queued publishing is **not** enabled by the action.
* The message appears in the intended chat only — never in both. When the two
  variables hold the same id, config resolution disables the channel
  (`channelChatId` becomes empty), so a channel test answers
  `400 Announcement channel is not configured` instead of posting into the group.
* One row in `telegram_marketing_sends` with `post_id = NULL`, the audience, the
  chat id, `status = 'sent'`, `attempt = 1` and the same message id.
* A failure answers `502` with Telegram's own description and writes
  `status = 'failed'` to the same table. Nothing is retried automatically.

---

## 5. Rollback / stop

Publishing is already off, so there is nothing to roll back for these two
messages. If anything else was switched on, one call stops it immediately:

```bash
curl -sS -X POST "$BASE/api/admin/marketing/control" \
  -H "Authorization: Bearer $JWT" -H "Content-Type: application/json" \
  -d '{"paused":true,"dryRun":true}'
```

That sets both gates; the worker then claims nothing on its next tick. Deleting
the two test messages in Telegram is a chat-side action, not a system change.

---

## 6. What these tests deliberately do NOT do

* They do not enable the worker, the queue, or scheduled publishing.
* They do not create, approve or schedule a post.
* They do not touch wallets, deposits, withdrawals, trading, referrals, KYC or
  subscriptions.
* They do not prove the **worker** path. That needs the Background Worker
  running (`worker_disabled` → `worker_tick` in its logs) and is verified
  separately by `node scripts/check-marketing-readiness.js` showing a healthy
  heartbeat, plus `docs/sql/marketing_rpc_rehearsal.sql` for the database
  contract.
